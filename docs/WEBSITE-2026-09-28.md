## 3. The load-bearing claim

with a fixed acceptance bar, so there is no single learner for a selection strategy to shape."

**Plain answer: this is asserted, not demonstrated. It is a reading of the results. No
analysis in the repo tests it.**

### 3.1 Provenance of the sentence
- It exists only in README.md, introduced by `eceed15` (2026-06-08 10:27). That commit is later than every study.
- Its components predate all data. They were a *design-time* argument for **not** running a learner-tracking curriculum; they were not offered as an explanation of any result.
  - `docs/handoffs/gepa_band_selection_handoff.md:76` (in `17f0775`, 2026-05-30): "line 7 re-samples *which candidate to mutate* stochastically from the Pareto frontier every iteration. There is no single 'current policy.' This is why the dynamic/curriculum version is a category mismatch".
  - `handoff:267`: "GEPA is a Pareto population with stochastic candidate selection (Algorithm 1 line 7), not a single improving learner, so 'a curriculum that tracks the learner' is a category mismatch, not a tuning problem."
  - `handoff:275` is a prepared answer to an anticipated interviewer question, making the same argument.
  - It is then repeated as a build constraint: `experiments/exp3_curriculum/CLAUDE_CODE_BUILD_PROMPT_exp3_curriculum.md:42-43`, `src/schedule.py:4-7`.

  - `docs/FINDINGS.md:60-65`: "Formatting frontier with bounded bidirectional gains".
  - `:203-207`: "the remaining diagnosed mechanism is the bounded bidirectional formatting gains on a bimodal substrate".
  - `:229-232`: "the lever is not falsified".

### 3.2 "Fixed acceptance bar" against the code and data
- **The fixed A=20 batch is an experimental manipulation, not a GEPA property.**
  - Stock GEPA accepts on the reflection minibatch (`handoff:74`: "if you bias which instances go into M, you also change the acceptance bar. This is the confound the decoupling fixes").
  - The repo swaps in A-batch scores (`src/decoupled_proposer.py:8-12,287-294`).
  - The `vanilla_coupled_gepa` arm keeps stock acceptance (`handoff:149`).
- **The threshold is not fixed; only the batch is.**
  - The gepa 0.1.1 gate is `if new_sum <= old_sum:` reject (`.venv/lib/python3.10/site-packages/gepa/core/engine.py:538-541`). `old_sum` is the selected parent's A-sum.
  - `prereg:89-90`: "the accept bar rises as the parent improves".
  - `docs/reports/PILOT_DERISK_REPORT.md:73-76`: "The proposer picks the parent via the Pareto candidate selector each iter, so this value reflects whichever parent was selected for THAT iteration, not a single monotonic trajectory."
  - Derived: every Exp 3 cell has 2-6 distinct `parent_a20` values, from 0.5619 to 0.6292.
- **The Pareto population is real in the runs.**
  - Parent selection is `ParetoCandidateSelector` (`src/curriculum_runner.py:226`, `src/run_gepa.py:491`).
  - It samples a non-dominated program weighted by front frequency (`.venv/.../gepa/gepa_utils.py:90-117`, `rng.choice` at `:116`).

### 3.3 Is there an analysis that tests it?
No. Specifically:
- Nothing logs or reports Pareto front size or membership. The only candidate count is `n_candidates` (accepts + 1) in Exp 1 cell summaries (`src/orchestrator.py:390`).
- No run uses a non-population selector. `CurrentBestCandidateSelector` exists in gepa (`.venv/.../gepa/strategies/candidate_selector.py:27-33`) but is never instantiated.
- Nothing ablates or varies the acceptance rule, A size, or threshold.

**The strongest evidence in the repo. All of it is consistent with the claim; none of it tests it:**
1. Exp 3 total accepts compress to 3.33–3.67 across arms, although timing differs (`RESULTS.md:43-46` vs `:34-37`).
2. Test F1 separation is below seed noise in every study: Exp 1 0.0121 vs 0.0395 (`analysis_chunk7/FINDINGS.md:3`); Exp 1b 0.0069 vs 0.0395 (`FINDINGS_hotpot_100.md:37`); Exp 3 0.0059 vs ≥0.0116 (derived from `RESULTS.md:56-59`).
3. The prior stated before any data (`handoff:125`): "the Pareto diversity machinery may matter more than minibatch composition."

**Evidence in the repo that cuts against parts of the sentence:**
- "Selection changes ... not outcomes (total accepts over budget)" (README.md:11-12): total accepts *did* differ by selection.
  - Exp 1: static_hard 3.3 vs static_frontier 7.3 (`analysis_chunk7/FINDINGS.md:34-35`).
  - Exp 1b: static_easy 0.0 vs static_hard 7.7 (`FINDINGS_hotpot_100.md:9-11`).
  - Only Exp 3 compresses.
- "Substrate-independent": no IFBench GEPA matrix exists (§2.3). The IFBench evidence consists of:
  - a 5-iteration pilot (0 accepts);
  - a single-arm N=40 de-risk run;
  - Phase 0, which has no population, so a population mechanism cannot explain its null.

## 7. OPEN QUESTIONS

1. **P1-P4 labels.**
   - P1's ordering fails in the means (static_medium 3.33 < hard_to_easy 4.00), while the e2h-latest half and the gap test hold. Is P1 "partially confirmed" or "not confirmed" under `prereg:105-108`?
   - P3: is it "inconclusive" (`:113-114`)?
2. **Does a mechanically forced zero count as P2 evidence?** easy_to_hard's phase-1 zero comes from skip_perfect (no proposals). The prereg's rationale ("near-zero signal") anticipated it, but the outcome was guaranteed by code, and the smoke run showed it before the matrix.
3. **"Fixed acceptance bar".** The batch is fixed and experimenter-imposed; the threshold moves with the sampled parent. Reword, drop, or keep with a definition?
4. **"Substrate-independent".** Without an IFBench GEPA matrix, and with Phase 0 involving no population, does the claim survive? Or should the writeup scope it to HotpotQA plus a single-reflection IFBench probe?
5. **README vs FINDINGS.**
   - README: "A clean null ... is the finding".
   - `docs/FINDINGS.md:229-232,275-279`: "not falsified", consistent with an effect smaller than seed noise.
   - The Exp 1 handoff: never "disproven".
   Which framing does the public writeup take?
6. **Mechanism framing.** Present the Pareto-population account as a hypothesis alongside FINDINGS.md's substrate-specific account (bimodal formatting frontier)? Or state which one the evidence favours? Neither has been tested.
7. **Seed-program baseline.** Should the writeup report the unoptimized seed test F1 of 0.6316? Several Exp 1 arm means sit at or below it.
8. **Citing the untracked `.env`.** The model ids are corroborated in tracked reports (§4); `.env` itself is not public.
9. **Exp 1 random vs Exp 3 random.** Exp 1 `random` averages 6.3 accepts per 44 iterations; Exp 3 `random` averages 3.33 per 40, under the same A=20 and b=3. Is this worth explaining (D_feedback composition, reused seeds, run-to-run variance)?
10. **Phase 0 addressability spec.** Does the "pre-registered" spec exist outside the repo, and can it be added before the writeup calls Phase 0 pre-registered?
11. **Exp 2 status wording.** "Shelved" (README) vs "not launched, operator's call" (reports). Should DEVIATIONS.md record the stop?
12. **The de-risk pilot and difficulty validation.** Should the public narrative mention them? They drove the Exp 3 pivot (`prereg:143-145`).
13. **Testing the mechanism.** Candidate tests:
    - rerun a cell with `CurrentBestCandidateSelector`;
    - log Pareto front size per iteration;
    - report accept rate per proposal;
    - vary A.
    Does any of this get run before publication, or does the writeup present the mechanism explicitly as untested?
14. **Errors in existing docs.** The wrong ranges at `docs/FINDINGS.md:44-50`, the prereg's "3.3 to 7.7 across bands", and the CHUNK14 TL;DR costs. Fix them in place, or only note them in the writeup? (Out of scope for this file.)
